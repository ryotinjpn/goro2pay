# ゴロゴロPay — User Stories

**Document Version**: 1.0
**Created**: 2026-05-07
**Scope**: MVP
**Persona**: 佐藤陽介（[personas.md](./personas.md) 参照）
**Breakdown Approach**: Epic-Based（ダメ化フェーズ0/1/2/3 + ダメ化UX 独立章）
**Acceptance Criteria Format**: Given / When / Then（Gherkin）
**Total Stories**: 23（Epic 0: 4, Epic 1: 7, Epic 2: 4, Epic 3: 5, Epic X: 3）

---

## INVEST 準拠の確認

本ドキュメントの各ストーリーは以下を満たす：

- **I**ndependent: 他ストーリーへの依存を最小化（前提関係はあっても結合せず、疎結合）
- **N**egotiable: 受入基準に書かれていない細部は実装者が裁量可能
- **V**aluable: ペルソナ「佐藤陽介」のダメ化体験に直接的価値をもたらす
- **E**stimable: 各ストーリーは見積もり可能な粒度で分解
- **S**mall: 1ストーリーは 1スプリントで完了できる粒度
- **T**estable: Given / When / Then で受入確認が自動/手動テスト可能

## ストーリー識別子規則

- **形式**: `US-{Epic}-{連番}`
- **Epic**: 0 / 1 / 2 / 3 / X
- 例: `US-1-03` = Epic 1 の 3 番目のストーリー

# 🎯 Epic 0 — 準備（ダメになる前の段取り）

**ペルソナのフェーズ**: ゴロゴロPay を使い始める直前  
**Goal**: 佐藤がゴロゴロPay を使える状態にする（認証・ダメ予算設定・初期画面表示）  
**関連機能要件**: FR-AUTH, FR-BUDGET

---

## US-0-01 — 新規登録でゴロゴロPay を始める

**タグ**: `#FR-AUTH-01` `#DegenerationUX:低摩擦オンボーディング`

**Story**:  
佐藤として、メールアドレスとパスワードで新規登録できるようにしたい。そうすれば、すぐにゴロゴロPay を使い始められる。

**Acceptance Criteria**:

```gherkin
Scenario: 新規ユーザが初回登録を行う
  Given 佐藤はまだゴロゴロPay のアカウントを持っていない
  And 佐藤はランディング画面を開いている
  When 佐藤は「はじめる」ボタンを押してメールアドレスとパスワードを入力する
  And 「登録」ボタンを押す
  Then Amazon Cognito User Pool にユーザが登録される
  And 佐藤はログイン済み状態でアプリのメイン画面へ遷移する
  And 登録から最初のボタン操作までの総タップ数は 5 回以下である
```

**Notes**: ダメ化UX の観点から、登録フローは最小限の摩擦にする。必須項目はメールアドレスとパスワードのみ。

---

## US-0-02 — ログインで前回の続きから始める

**タグ**: `#FR-AUTH-02` `#FR-AUTH-03`

**Story**:  
佐藤として、登録済みのメールアドレスとパスワードでログインできるようにしたい。そうすれば、前回の続きから使える。

**Acceptance Criteria**:

```gherkin
Scenario: 既存ユーザがログインする
  Given 佐藤は Cognito に登録済みのアカウントを持っている
  When 佐藤はログイン画面でメールアドレスとパスワードを入力して「ログイン」を押す
  Then 佐藤は認証され JWT を受け取る
  And 佐藤はメイン画面へ遷移する
  And セッションは少なくとも 1 時間維持される

Scenario: パスワードを間違える
  Given 佐藤は Cognito に登録済みのアカウントを持っている
  When 佐藤は誤ったパスワードを入力して「ログイン」を押す
  Then 佐藤は「メールアドレスまたはパスワードが違います」とエラーを見る
  And 佐藤はメイン画面へ遷移しない
```

---

## US-0-03 — ダメ予算を設定する

**タグ**: `#FR-BUDGET-01` `#FR-BUDGET-02` `#DegenerationUX:コミットメント`

**Story**:  
佐藤として、月間のダメ予算（円）を設定できるようにしたい。そうすれば、毎月いくらまでダメになれるかが決まる。

**Acceptance Criteria**:

```gherkin
Scenario: 初回起動時にダメ予算を設定する
  Given 佐藤は新規登録直後でダメ予算未設定
  When 佐藤は「ダメ予算設定」画面を開き 30,000 円を入力して「設定」を押す
  Then 月間ダメ予算が 30,000 円として保存される
  And 仮想ウォレット残高が 30,000 円として初期化される
  And 佐藤はメイン画面へ遷移する

Scenario: 予算を変更する
  Given 佐藤は月間予算 30,000 円を設定済み
  When 佐藤は設定画面から予算を 50,000 円に変更する
  Then 月間予算は 50,000 円として保存される
  But 当月の残高はその時点の値から変更されない（翌月のリセットから適用）
```

---

## US-0-04 — 初回メイン画面を表示する

**タグ**: `#FR-AUTH-03` `#FR-UX-01`

**Story**:  
佐藤として、ログイン後にメイン画面を表示できるようにしたい。そうすれば、今の残高と「ご飯めんどくさい」ボタンが一目で見える。

**Acceptance Criteria**:

```gherkin
Scenario: ログイン後にメイン画面が表示される
  Given 佐藤はログイン済みで、ダメ予算 30,000 円を設定済み
  When 佐藤はアプリを開く
  Then 画面上部に「残りダメ予算: ¥30,000」が大きく表示される
  And 画面中央に「ご飯めんどくさい」ボタンが大きく配置される
  And メイン画面の初期表示は 5 秒以内に完了する
  And メイン画面に他の操作要素（メニュー・広告等）は表示されない（低摩擦）
```

# 🎯 Epic 1 — ボタンを押すだけ（ダメ化フェーズ1: 即時解決の快感）

**ペルソナのフェーズ**: 使用開始〜初月。「考えずに楽できる快感」の発見。  
**Goal**: ボタン1回で代行手配を完結させ、「即時解決」の体験を提供する。  
**関連機能要件**: FR-ORDER, FR-BUDGET, FR-LEARNING

---

## US-1-01 — 「ご飯めんどくさい」ボタンを押して代行手配する（本プロジェクトのコアストーリー）

**タグ**: `#FR-ORDER-01` `#FR-ORDER-02` `#FR-ORDER-03` `#FR-ORDER-04` `#DegenerationUX:即時解決`

**Story**:  
佐藤として、「ご飯めんどくさい」ボタンを1回押すだけで、自動的に最適なデリバリーが手配されるようにしたい。そうすれば、考えることなくご飯が届く。

**Acceptance Criteria**:

```gherkin
Scenario: ボタン押下で代行手配が完了する
  Given 佐藤はログイン済みで、残高 30,000 円を持つ
  When 佐藤はメイン画面の「ご飯めんどくさい」ボタンを 1 回押す
  Then バックエンドは Amazon Bedrock (Claude) に履歴・時刻を渡し最適なデリバリープランを推論する
  And DeliveryAdapter.placeOrder() が MockDeliveryAdapter 実装で呼ばれる
  And 注文金額がウォレット残高から減算される
  And 完了画面に「注文完了: <店舗名> <メニュー名> ¥<金額> - 残りダメ予算 ¥<残高>」が表示される
  And ボタン押下から完了画面表示までの体感時間は 3 秒以内である
  And 操作タップ数はボタン押下の 1 回のみである
```

**Notes**: 本ストーリーは MVP の**コア**。審査員のデモで最も重要。

---

## US-1-02 — 残高を常に視認できる

**タグ**: `#FR-BUDGET-05` `#DegenerationUX:予算可視化`

**Story**:  
佐藤として、メイン画面で常に「残りダメ予算」を大きく視認できるようにしたい。そうすれば、あとどれくらいダメになれるかが一目で分かる。

**Acceptance Criteria**:

```gherkin
Scenario: メイン画面で残高が常時可視化される
  Given 佐藤の残高は現時点で 28,800 円である
  When 佐藤はメイン画面を開く
  Then 画面上部に「残りダメ予算: ¥28,800」が視認性の高いフォントサイズで表示される
  And ボタン押下で金額が減算された直後、表示は即座に更新される（stale state を表示しない）
```

---

## US-1-03 — 注文履歴に代行手配が記録される

**タグ**: `#FR-ORDER-06` `#FR-LEARNING-01`

**Story**:  
佐藤として、過去の代行手配が履歴として自動的に記録されるようにしたい。そうすれば、後から「いつ何を手配したか」が分かるし、システムは将来の先回り提案のためにこれを学習できる。

**Acceptance Criteria**:

```gherkin
Scenario: 代行手配が履歴に保存される
  Given 佐藤は「ご飯めんどくさい」ボタンで注文完了した
  When バックエンドが注文を受理する
  Then DynamoDB の履歴テーブルに以下が記録される:
    | ユーザID      |
    | カテゴリ (food) |
    | 店舗名        |
    | メニュー名     |
    | 金額          |
    | 注文日時      |
    | 曜日          |
  And 履歴は直近 3 ヶ月分を保持する（DynamoDB TTL）
```

---

## US-1-04 — 残高不足時に今月ダメになれないことを知る

**タグ**: `#FR-BUDGET-06` `#FR-METRICS-04` `#DegenerationUX:無力感予告`

**Story**:  
佐藤として、残高が不足しているときには代行手配を失敗させてほしい。そうすれば、「ダメ予算」というコンセプトが機能する。

**Acceptance Criteria**:

```gherkin
Scenario: 残高不足で注文が失敗する
  Given 佐藤の残高は 500 円である
  When 佐藤は「ご飯めんどくさい」ボタンを押す
  And バックエンドが推論した注文予定額は 1,200 円である
  Then ウォレットからの引き落としは実行されない
  And 佐藤は「今月、ダメになれません（残高: ¥500）」という画面を見る
  And 注文は外部アダプタに送られない
```

---

## US-1-05 — 二重引き落としを防ぐ

**タグ**: `#NFR-REL-02` `#DegenerationUX:信頼性維持`

**Story**:  
佐藤として、ボタンを連打したときに金額が重複引き落としされないようにしたい。そうすれば、安心してボタンを押せる。

**Acceptance Criteria**:

```gherkin
Scenario: 同一リクエストの再送で残高は 1 回分しか減らない
  Given 佐藤の残高は 30,000 円である
  When 佐藤は「ご飯めんどくさい」ボタンを連打して 3 回リクエストを送る
  And すべてのリクエストに同一の冪等性キーが付与されている
  Then ウォレット残高は 1,200 円しか減らない（合計 28,800 円）
  And 注文履歴には 1 件のみ記録される
  And 2 回目以降のレスポンスは 1 回目と同じ結果を返す（orderId 含む）
```

---

## US-1-06 — 残高が負にならない

**タグ**: `#NFR-REL-01` `#DegenerationUX:信頼性維持`

**Story**:  
佐藤として、残高がマイナスになる事態が起きないようにしたい。そうすれば、「ダメ予算」が正しく機能する。

**Acceptance Criteria**:

```gherkin
Scenario: 残高を超える注文は拒否される
  Given 佐藤の残高は 1,000 円である
  When バックエンドの推論で注文予定額が 1,200 円となる
  Then DynamoDB の条件付き書き込み（balance >= amount）により減算が拒否される
  And ウォレット残高は 1,000 円のまま変化しない
  And US-1-04 の「ダメになれません」画面が表示される
```

---

## US-1-07 — 注文完了画面から自動でメインへ戻る

**タグ**: `#FR-UX-04` `#DegenerationUX:低摩擦`

**Story**:  
佐藤として、注文完了画面から自動的にメイン画面へ戻るようにしたい。そうすれば、「戻る」の操作すら不要になる。

**Acceptance Criteria**:

```gherkin
Scenario: 完了画面から自動遷移
  Given 佐藤の注文が完了し完了画面が表示されている
  When 5 秒が経過する
  Then 画面は自動でメイン画面へ遷移する
  And 佐藤は「戻る」「メインへ」等のボタンを押す必要がない
```

# 🎯 Epic 2 — ボタンすら不要（ダメ化フェーズ2: 先回り提案）

**ペルソナのフェーズ**: 使用開始 2〜4ヶ月目。依存の深化。  
**Goal**: ユーザの行動履歴から先回り提案を生成し、「考える」工程すら奪う。  
**関連機能要件**: FR-LEARNING, FR-SUGGEST

---

## US-2-01 — アプリを開いた瞬間に先回りサジェストが表示される

**タグ**: `#FR-SUGGEST-01` `#FR-SUGGEST-02` `#DegenerationUX:先回り提案`

**Story**:  
佐藤として、アプリを開いた瞬間、過去の利用傾向から「そろそろ◯◯めんどくさいですよね？」というサジェストカードが表示されるようにしたい。そうすれば、自分で「何をしたい」と考えなくていい。

**Acceptance Criteria**:

```gherkin
Scenario: 履歴十分で起動時サジェストが出る
  Given 佐藤は過去 14 日間で food カテゴリを平日 19 時前後に 5 回以上利用している
  When 佐藤は平日 18:55 にアプリを開く
  Then バックエンドは Amazon Bedrock に履歴・時刻を渡し次候補の推論をリクエストする
  And メイン画面上部に「そろそろご飯めんどくさいですよね？」というサジェストカードが表示される
  And サジェストカード内に「YES（注文）」の 1 タップボタンがある
  And サジェストカードには推奨される店舗・メニュー・金額のプレビューが含まれる
```

---

## US-2-02 — 履歴が不十分なときはサジェストを出さない

**タグ**: `#FR-SUGGEST-04`

**Story**:  
佐藤として、まだ利用履歴が少ないときには無理にサジェストを出さないでほしい。そうすれば、的外れな提案で信頼を失わない。

**Acceptance Criteria**:

```gherkin
Scenario: 履歴 0 件の新規ユーザ
  Given 佐藤は新規登録直後で利用履歴が 0 件
  When 佐藤はアプリを開く
  Then サジェストカードは表示されない
  And デフォルトの「ご飯めんどくさい」ボタンのみが表示される

Scenario: 履歴が少なすぎる
  Given 佐藤は登録後、過去に 1 回しか注文していない
  When 佐藤はアプリを開く
  Then サジェストカードは表示されない（最小履歴件数に達していない）
```

---

## US-2-03 — サジェストカードから 1 タップで注文する

**タグ**: `#FR-SUGGEST-03` `#DegenerationUX:思考削減`

**Story**:  
佐藤として、サジェストカードの「YES」ボタンを 1 タップするだけで、サジェストされた内容で注文できるようにしたい。そうすれば、ボタンを押す以上の判断が不要になる。

**Acceptance Criteria**:

```gherkin
Scenario: サジェストからの 1 タップ注文
  Given 佐藤のメイン画面に「そろそろご飯めんどくさいですよね？（CoCo壱 カレーライス ¥1,200）」のサジェストカードが表示されている
  When 佐藤はカードの「YES」ボタンを 1 タップする
  Then US-1-01 と同等の代行手配フローが実行される（Bedrock 推論はスキップまたは検証のみ）
  And ウォレット残高が減算される
  And 完了画面に「注文完了: CoCo壱 カレーライス ¥1,200 - 残りダメ予算 ¥<残高>」が表示される
  And サジェスト受諾からの総タップ数は 1 回のみである
```

---

## US-2-04 — 行動履歴が蓄積されて学習される

**タグ**: `#FR-LEARNING-01` `#FR-LEARNING-02`

**Story**:  
佐藤として、使えば使うほどシステムが私の行動パターンを学習するようにしたい。そうすれば、サジェストの精度が上がり、私は何も考えなくなる。

**Acceptance Criteria**:

```gherkin
Scenario: 代行手配のたびに履歴が蓄積される
  Given 佐藤は過去 30 日間で 20 回の代行手配を行った
  When 佐藤が 21 回目の代行手配を完了する
  Then 履歴テーブルに 21 件目のレコードが追加される
  And Bedrock へのサジェスト推論プロンプトに直近 30 件（または 3 ヶ月以内）の履歴が含まれる

Scenario: 古い履歴は自動削除される
  Given 佐藤は 4 ヶ月前の代行手配記録を持つ
  When DynamoDB の TTL が動作する
  Then 3 ヶ月を超える古い履歴は自動的に削除される
```

# 🎯 Epic 3 — 完全に人がダメになる（ダメ化フェーズ3: 退化と依存ループ）

**ペルソナのフェーズ**: 使用開始 5ヶ月目以降。無力感の自覚と、それでも止められないループ。  
**Goal**: 予算消化状況を可視化し、残高枯渇時の無力感を体験させ、翌月予算の増額誘導で依存ループを完成させる。  
**関連機能要件**: FR-METRICS, FR-BUDGET-04（リセット）

---

## US-3-01 — 今月のダメ化回数を見て優越感と空虚感を同時に感じる

**タグ**: `#FR-METRICS-01` `#DegenerationUX:ダメ化可視化`

**Story**:  
佐藤として、今月何回ダメになったかを一目で見られるようにしたい。そうすれば、自分の退化具合を実感できる（そしてそれを楽しむ）。

**Acceptance Criteria**:

```gherkin
Scenario: メイン画面で今月のダメ化回数が見える
  Given 佐藤は今月 15 回の代行手配を行った
  When 佐藤はメイン画面を開く
  Then 画面の適切な位置に「今月のダメ化回数: 15 回」が表示される
  And 表示は残高表示と並列で視認性高く配置される
```

---

## US-3-02 — ダメ予算消化率を見る

**タグ**: `#FR-METRICS-02` `#FR-METRICS-03` `#DegenerationUX:不安演出`

**Story**:  
佐藤として、ダメ予算の消化率をパーセントで見られるようにしたい。そうすれば、「あとどれくらいダメになれるか」を率で把握できる。また、消化率が高いときには強調表示で不安を感じられるようにしたい。

**Acceptance Criteria**:

```gherkin
Scenario: 消化率が通常時
  Given 佐藤の月間ダメ予算は 30,000 円で、残高は 21,000 円である
  When 佐藤はメイン画面を開く
  Then 「ダメ予算消化率: 30%」が通常色で表示される

Scenario: 消化率が 80% を超えて不安を煽る
  Given 佐藤の月間ダメ予算は 30,000 円で、残高は 5,000 円である
  When 佐藤はメイン画面を開く
  Then 「ダメ予算消化率: 83%」が警告色（赤系）で強調表示される
  And 画面の視覚的演出で佐藤の不安を煽る
```

---

## US-3-03 — 残高 0 円時に「今月ダメになれません」画面を見る

**タグ**: `#FR-METRICS-04` `#DegenerationUX:無力感体験`

**Story**:  
佐藤として、残高が 0 円になったときは「今月、ダメになれません」と明示されるようにしたい。そうすれば、自力で何かをする必要に直面した自分の無力感を体験できる。

**Acceptance Criteria**:

```gherkin
Scenario: 残高 0 円時のメイン画面
  Given 佐藤の月間ダメ予算は 30,000 円で、残高は 0 円である
  When 佐藤はメイン画面を開く
  Then 「ご飯めんどくさい」ボタンは無効化される（タップできない or タップするとモーダル）
  And 画面に「今月、ダメになれません」というメッセージが大きく表示される
  And 画面に「今月のダメ化サマリ: 面倒回数 <N> 回、消化額 ¥<金額>」が表示される
  And 画面に翌月予算の増額提案モーダル（US-3-04）が表示される
```

---

## US-3-04 — 翌月予算の増額誘導モーダルで意思薄弱になる

**タグ**: `#FR-METRICS-04` `#FR-METRICS-05` `#DegenerationUX:増額誘導`

**Story**:  
佐藤として、残高が尽きたとき、翌月予算を今より多く設定するモーダルを見たい。そうすれば、「来月こそは、もっとダメになれる」と思って増額してしまう。これが依存ループの完成である。

**Acceptance Criteria**:

```gherkin
Scenario: 残高 0 円到達時に増額提案モーダルが出る
  Given 佐藤の残高が 0 円に到達した
  When 佐藤がメイン画面を開く（または手配を試みる）
  Then 画面上に翌月予算増額提案モーダルが表示される
  And モーダルには「翌月予算を増額しますか？ 推奨: ¥50,000」のコピーが表示される
  And モーダルには「OK（増額する）」「あとで」の 2 ボタンがある
  And 「OK」を押すと翌月からの予算が推奨額にセットされる
  And 「あとで」を押すとモーダルは閉じるが、次回起動時に再表示される

Scenario: 増額推奨値の算出
  Given 佐藤の今月消化額は 30,000 円（現予算と同値）
  Then 推奨増額値は現予算の +50% または +20,000 円のうち小さい方として算出される（例: 30,000 → 45,000）
  But 推奨額はペルソナを過度に圧迫しないよう上限を設ける（本 MVP では 100,000 円）
```

## US-3-05 — 月初にダメ予算が自動リセットされる

**タグ**: `#FR-BUDGET-04`

**Story**:  
佐藤として、毎月 1 日に自動的にダメ予算がリセットされるようにしたい。そうすれば、新たな月がまた始まり、ダメ化サイクルが繰り返される。

**Acceptance Criteria**:

```gherkin
Scenario: 月初リセット
  Given 佐藤の月間予算は 50,000 円である
  And 前月末の残高は 0 円だった
  When 日付が 2026-06-01 00:00 JST に変わる
  Then EventBridge Scheduler が monthlyReset Lambda を起動する
  And 佐藤を含む全ユーザの残高が各自の月間予算額（佐藤は 50,000 円）にリセットされる
  And リセット操作がシステムログ（CloudWatch Logs）に記録される

Scenario: 月初リセットが失敗した場合
  Given monthlyReset Lambda がエラーで失敗した
  When 運用者が CloudWatch Logs でエラーを検知する
  Then 運用者は手動リカバリ手順（設計書記載）に従ってリセットを再実行できる
```

# 🎯 Epic X — ダメ化UX 体験ストーリー（独立章）

本章は **機能ストーリーの裏側にある「感情・体験」** を独立のユーザストーリーとして定義する。技術的実装は機能ストーリー群と重複するが、**審査観点「創造性とテーマ適合性」への訴求** として独立章を立てる。

---

## US-X-01 — 決定疲れから解放される快感を得る（フェーズ1体験）

**タグ**: `#DegenerationUX:決定疲れ解放` `#Epic1`

**Story**:  
佐藤として、「何を食べるか」を選ぶ工程がゴロゴロPay によって消滅する体験をしたい。そうすれば、現代人の宿痾である決定疲れから解放される快感を得られる。

**Acceptance Criteria**:

```gherkin
Scenario: 決定疲れ解放の体験
  Given 佐藤は仕事から帰宅し、認知エネルギーを使い切った状態である
  When 佐藤はアプリを開き「ご飯めんどくさい」ボタンを 1 回押す
  Then 佐藤は「どの店にする？」「何を食べる？」「いくら払う？」の 3 つの意思決定から解放される
  And 佐藤はボタン押下から完了まで、1 回もテキスト入力・選択肢比較を行わない
  And 佐藤は 3 秒以内に「終わった」という感覚を得る
  # この体験は US-1-01 を通じて実現される
```

**Notes**: 体験の核は「3つの意思決定の消滅」である。

---

## US-X-02 — 自分より自分を知る AI に委ねる心地よさを得る（フェーズ2体験）

**タグ**: `#DegenerationUX:自己委譲` `#Epic2`

**Story**:  
佐藤として、「アプリの方が自分より自分のことを分かっている」と感じる瞬間を得たい。そうすれば、自己決定の責任を手放し、システムに委ねる心地よさを体験できる。

**Acceptance Criteria**:

```gherkin
Scenario: 自己委譲の体験
  Given 佐藤は過去 30 日で平日 19 時前後に food カテゴリを 10 回以上利用している
  When 佐藤は平日 18:55 に疲れ切った状態でアプリを開く
  Then サジェストカード「そろそろご飯めんどくさいですよね？」が、佐藤が思考する前に既に表示されている
  And サジェスト内容は佐藤の過去の傾向（よく選ぶ店舗・金額帯）に合致する
  And 佐藤はサジェストを見た瞬間、「分かってくれてる」という感覚を得る
  And 佐藤は「YES」を押す決定を 2 秒以内に完了する
  # この体験は US-2-01, US-2-03 を通じて実現される
```

**Notes**: 体験の核は「AI に先回りされる心地よさ」である。

---

## US-X-03 — 自力で何もできない自分に気づき、それでも戻れないループを完成する（フェーズ3体験）

**タグ**: `#DegenerationUX:退化ループ` `#Epic3`

**Story**:  
佐藤として、残高が尽きて「今月ダメになれない」状況に直面したとき、自分で何かをしようとしても何も思いつかない無力感を体験したい。そしてその無力感から、翌月予算の増額で依存を深める決断をする自分に気づきたい。

**Acceptance Criteria**:

```gherkin
Scenario: 退化ループの自覚
  Given 佐藤は残高 0 円で「今月ダメになれません」画面を見ている
  And 佐藤は今月の代行手配回数 47 回と表示されている
  When 佐藤は翌月予算増額モーダル「¥30,000 → ¥50,000」を見る
  Then 佐藤は「増額しなければ、自分で何かをしなければならない」と考える
  And 佐藤は「自分で何かを」を具体的に言語化できない（思考停止の体験）
  And 佐藤は「OK（増額する）」を押す
  And システムは翌月から予算 50,000 円を適用する
  # この体験は US-3-03, US-3-04 を通じて実現される
```

**Notes**: 体験の核は「自力では思いつかないことに気づき、増額で逃げる」。退化ループの完成点。idea.md の「翌月は予算を増やしてしまう」に直接対応。
